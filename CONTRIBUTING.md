# Contributing to Bornier

## Ground rules

- **English only**: code, comments, documentation, file names, commit messages.
- **Licenses**: every file carries SPDX headers (`SPDX-License-Identifier`, `SPDX-FileCopyrightText`).
  Files that cannot hold a header are covered by [`REUSE.toml`](REUSE.toml).
  Hardware is CERN-OHL-W-2.0, firmware and tools MPL-2.0, documentation CC-BY-4.0.
- **CMake only.** The CMake files and the GNU Arm toolchain are the whole build; IDE project
  files are not committed.
- **Generated files are not edited by hand**: the register headers in
  [`firmware/devices/`](firmware/devices/STM32H523/README.md).

## Building the firmware

The firmware is C++26 and needs GCC 16. The reference toolchain is
[arm-none-eabi-toolchain 16.2.0-1](https://github.com/Otatiaro/arm-none-eabi-toolchain/releases/tag/v16.2.0-1)
(GCC 16.2.0, binutils 2.47, newlib 4.6), built for Linux and Windows x86_64 and used by CI. On
Debian 13 (the reference platform, also used by CI):

```sh
sudo apt install cmake ninja-build curl xz-utils
curl -fsSLO https://github.com/Otatiaro/arm-none-eabi-toolchain/releases/download/v16.2.0-1/arm-none-eabi-toolchain-16.2.0-1-linux-x86_64.tar.xz
echo "a4fb8cc55be7e3a641ffd7cd8e396762b1ee77a7ff19411884eed0a44585b2b0  arm-none-eabi-toolchain-16.2.0-1-linux-x86_64.tar.xz" | sha256sum -c
tar -xf arm-none-eabi-toolchain-16.2.0-1-linux-x86_64.tar.xz -C ~/.local
export PATH=~/.local/arm-none-eabi-toolchain-16.2.0-1/bin:$PATH
git clone --recurse-submodules https://github.com/bornier-dev/bornier.git
cd bornier
cmake --preset debug   && cmake --build --preset debug
cmake --preset release && cmake --build --preset release
```

On other systems, install CMake, Ninja and that toolchain (or another GCC 16 for arm-none-eabi),
with `arm-none-eabi-gcc` on the `PATH`.

Images land in `build/<preset>/firmware/...` as `.elf`, `.bin` and `.map`.

### EtherCAT stack

The EtherCAT protocol is handled by the Beckhoff EtherCAT Slave Stack Code (SSC). It is licensed
separately by the EtherCAT Technology Group to its members and is **not part of this
repository**: never commit any of its files, nor code generated from it. The firmware only holds
the hardware access layer under it ([`firmware/boards/base/ssc_hw.h`](firmware/boards/base/ssc_hw.h))
and the application above it ([`firmware/boards/base/ssc_appl.cpp`](firmware/boards/base/ssc_appl.cpp)).

The SSC Tool also generates an application file from the object dictionary, rewritten whole at
each generation. The build renames, in that file only, the functions the application defines
(`BORNIER_SSC_APPLICATION` names the file): nothing is edited in generated code.

Without the stack, everything above builds and the EtherCAT images are left out. With a stack
generated by the SSC Tool, point the build at its source folder:

```sh
cmake --preset debug -DBORNIER_SSC_DIR=/path/to/generated/src && cmake --build --preset debug
```

`firmware/tests/ethercat_preop` then runs the stack on the base board; it is checked from an
EtherCAT master, which must read the slave identity and bring it to PREOP, and with LinuxCNC and
lcec to OP, the axes walked through their CiA402 states.

## Firmware rules

- **C++26 on the OpSy RTOS** ([`firmware/third_party/opsy`](firmware/third_party/opsy)), no HAL or CMSIS: peripherals are reached
  through the generated register headers.
- **Warnings are errors.** The warning set in [`firmware/CMakeLists.txt`](firmware/CMakeLists.txt)
  applies to all code, OpSy included, and linker warnings are fatal too. Fix a warning at its
  source; disable one only if it is pure noise, and say why next to the flag.
- **Debug and release are both tested on target.** A bug that shows only with optimization almost
  always means undefined behavior or approximate code, not a compiler problem.
- **Hardware and concurrency:**
  - memory-mapped registers are accessed through `volatile`, which the generated headers do;
  - data shared between an interrupt and a task is a `std::atomic` or is protected by a lock,
    never a plain variable;
  - a read-modify-write on a register that an interrupt may also modify uses the atomic
    operators (`reg |= value | atomic`, `reg <<= field || atomic`). They protect against
    interrupts and tasks on the same core, not against DMA or another bus master
    ([`firmware/tests/atomic_mmio`](firmware/tests/atomic_mmio/main.cpp)).
- **Style**: match the surrounding code (tabs in C++, four spaces in CMake, comment density,
  naming).

## Flashing and debugging

A debug probe is needed only for the first flash and for debugging; boards then update over
EtherCAT (FoE). Flashing and debugging use probe-rs, which drives ST-Link, J-Link and
CMSIS-DAP probes.

```sh
probe-rs download --chip STM32H523VE --verify build/debug/firmware/examples/blink/blink.elf
probe-rs reset --chip STM32H523VE
```

On Windows, probe-rs needs the WinUSB driver on a J-Link, which replaces the SEGGER driver. To
keep the SEGGER driver, flash with J-Link Commander (`JLink.exe`, `JLinkExe` on Linux) from the
SEGGER J-Link software:

```sh
JLinkExe -device STM32H523VE -if SWD -speed 4000 -autoconnect 1
J-Link> loadfile build/debug/firmware/examples/blink/blink.elf
J-Link> r
J-Link> g
J-Link> exit
```

On Linux, install [`tools/udev/60-debug-probes.rules`](tools/udev/60-debug-probes.rules) so the
probe is usable without root:

```sh
sudo cp tools/udev/60-debug-probes.rules /etc/udev/rules.d/
sudo udevadm control --reload && sudo udevadm trigger
```

To debug, start the GDB server, then connect GDB:

```sh
probe-rs gdb --chip STM32H523VE
arm-none-eabi-gdb build/debug/firmware/examples/blink/blink.elf \
    -ex "target extended-remote 127.0.0.1:1337" \
    -ex "set mem inaccessible-by-default off" \
    -ex "load"
```

- `set mem inaccessible-by-default off` is needed to read peripheral registers: the memory map
  probe-rs gives GDB does not include them.
- After `load` the program counter is already on the reset handler; avoid `monitor reset` in
  the session.
- The GDB server holds the probe until it exits: stop it before flashing with
  `probe-rs download`, which otherwise fails with a USB error.

## Tracing

Images report through a trace, not through text: each event is a plain struct written with
`bornier::trace::emit()` ([`firmware/trace/bornier/trace.hpp`](firmware/trace/bornier/trace.hpp))
into a ring in RAM, with the cycle counter. OpSy adds its own events (task switches, interrupts,
faults). [Kymo](firmware/third_party/kymo) reads the ring through the debug port (SWD) while the
program runs and decodes each event with the ELF, which must be the one flashed. Both presets
keep debug information in the ELF for that; it does not change the code.

Build the host programs with Rust (cargo), then record:

```sh
cargo build --release --manifest-path firmware/third_party/kymo/host/Cargo.toml
kymo record --probe jlink --chip STM32H523VE --clock 250000000 --duration 5 \
    --elf build/debug/firmware/examples/blink/blink.elf
```

`--clock` is the core clock of the image, which times the events; `--probe probe-rs` drives
any probe probe-rs supports, but not the ST-Link library on an STM32H5, which halts the core.
`kymo-ui` (`host/ui`) shows a recording as a timeline.

## On-target tests

Hardware-in-the-loop scripts and the list of tests are in [`tools/hil/`](tools/hil/README.md).
Run them on the debug and the release image.

## Commits and pull requests

- One topic per pull request; commit messages in English, imperative mood.
- CI builds both presets and must pass.
- For a firmware change, state in the pull request which boards and which on-target tests were
  run, on which images.

## Vendor ID and forks

Official releases carry the Bornier EtherCAT Vendor ID. Forks that distribute hardware or
firmware must use their own Vendor ID.
